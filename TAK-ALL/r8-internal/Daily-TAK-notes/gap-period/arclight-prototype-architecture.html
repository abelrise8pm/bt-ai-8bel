One-sentence version: Two ATAK devices share mission data — team locations, routes, enemy markers — directly with each other, encrypted, with no server in the middle. Two kinds of data, two lanes

My read of the key design choice: Arclight treats "facts that must be exactly right" differently from "where everyone is right now." This keeps the network from drowning in old location pings.

Durable truth

"MST documents" · reliable, must converge exactly
  • team member metadata (callsign, role)
  • missions & summaries
  • routes
  • hostile metadata (label, type, confidence)
  • GRG / source-data manifests
Sent reliably — confirmed, retried if needed, until both devices match.

Live position

"heartbeat telemetry" · latest-value, refreshes constantly
  • where each teammate is right now (PLI)
  • where each hostile is right now
Not stored/retried. If one update is missed, the next heartbeat just carries the newer position — no backlog of stale pings.

Why a PM should care: Kevan calls this "a stable foundation to build on," and flags "data fusion from multiple sensors with confidence and prioritization" as a known next improvement — a candidate consideration, not something he built.

My read: the demo used "a deterministic Kotlin parser" (plain code). Kevan says the intent/action mapping "should move into mission-domain logic over time," with an optional on-device or cloud LLM as a future, swappable add-on — both candidate items for the team, not finished work.

Then the smart part: when a hostile is dropped near a route, the route turns orange to flag the threat — mission meaning driving what the map shows.

Where Kevan says it's headed

⚠️ This is the target / future structure Kevan sketched, not what's built today. He explicitly said "everything here is up for grabs as far as moving it from prototype to reality." Treat these as considerations for the team, not committed work.

Today the mission logic and the ATAK screen code live together inside Team Presence. The proposed clean-up splits responsibilities so the bulk could be shared across ATAK, WinTAK, WebTAK, etc. — Kevan's "TAK-X / TAK-Y / TAK-Z" idea, built in Kotlin Multiplatform Compose.

arclight-sdk
the generic, mission-agnostic sync doorway
arclight-atak-runtime
the Android engine: radios, identity, crypto, routing
mission-core
"pure mission logic" — routes, hostiles, rules — reusable across platforms
mission-arclight-adapter
the bridge that hides sync details from mission features
mission-llm-adapter
optional language → command translator (on-device or cloud)
mission-atak-plugin
just the ATAK screen: panels, taps, markers

Kevan's umbrella name for the whole stack: "SOFTAK SDK" — "whether we ever officially publish it or not." Plain read: a reusable kit that could power mission features on many TAK flavors, not just Android.
